How it works

The technical details, in plain terms.

You paste a GitHub username. Every public repository that account owns is scanned for exposed credentials and for insecure GitHub Actions workflows, a few of them are read line by line by an AI, and you get back one report. It costs nothing to run and it is meant to stay that way.

The goal

Most security tools either cost money, need an account, or hand you a wall of findings you cannot tell apart. This one is free, needs no sign-up, never runs your code, and tries hard to only tell you about things that are actually real. The report is public to anyone with the link and is deleted after 30 days.

What runs on every repository

  • Secret scan. Gitleaks 8.30.1 reads every file under 20 MB and looks for the shapes of leaked credentials: API keys, tokens, private keys. It runs at one pinned version so the report can say exactly what was and was not checked.
  • Workflow audit. Zizmor 1.29.0 checks your GitHub Actions workflow files for security problems: actions pinned to a tag instead of a commit, jobs handed more permissions than they use, checkouts that leak their own credentials, untrusted input reaching a run step.

Two more checks exist in the code and are not switched on yet: dependency vulnerabilities and deeper static analysis.

DeepScan: the AI code review

The three repositories you pushed to most recently carry the DeepScan badge; forks and empty repositories never take a slot. For those, a model reads the actual code, line by line, looking for the kinds of bugs a pattern scanner cannot see: SQL injection, broken authentication, unsafe deserialization, path traversal, and other classes it is trained on. On real repositories this has found genuine SQL injection and a login flow that stored a password in a cookie, neither of which a secret scanner could ever catch.

Reading whole repositories with a capable model is the expensive part, so it is rationed. Three separate limits are worth keeping apart, because they are easy to confuse. Each scan DeepScans at most three repositories, the ones you pushed to most recently. Across everyone using the service, about 100 repositories get a DeepScan each day, and that resets overnight. Separately, the service accepts at most 240 scans a day in total, a cap enforced in the database rather than in the page. The secret scan and the workflow audit are cheap and run on every repository in every scan, however many you have.

Why you can trust a finding

A single model saying "this looks like a bug" is not enough to put on a security report, so nothing a model raises is published on its own word. Every AI finding goes through two gates:

  • Grounding. The system checks that the exact line and code the model pointed at really exist in the repository. Anything it cannot prove it saw is discarded.
  • A council. Separate models from different companies then vote on whether the finding is real. They never see each other's answers. A finding is only published when a majority of the ones that answered agree, and a finding no model could confirm is dropped.

The same council also reviews the secret scan's findings and can remove a false alarm, but only when the two most trusted models both agree it is one, and only for that single finding: a fake key can be removed while a real key on the next line stays. When a model's provider is unreachable, whoever answered decides and the repository is marked as partly reviewed, so the report never hides that the check behind a finding was thinner than usual.

The core idea: the scanner never trusts the code

The repository being scanned is treated as hostile. It runs inside a sealed sandbox with no network access, and the only thing allowed to leave that sandbox is numbers: a code for which rule matched and a rough count. The rule's name, its severity, and the advice you read are all looked up on the trusted side from a fixed list. This is what stops a malicious repository from writing anything of its own into a report, and it is why a model can take part as just another checker without being able to invent a finding or put words on the page.

The one exception, made deliberately, is that a short, comment-stripped excerpt around a secret-scan finding is sent to the council so it can judge whether the value is real. The secret itself is blanked out first; what the model learns about the value is its length and whether it contains common placeholder words like "example".

The architecture

  • The website and database run on a free Cloudflare Worker with a D1 database. This serves the page, accepts scans, and stores the ledger of what happened to each repository.
  • The scanning compute runs on free GitHub Actions minutes. A queue hands work out; a run picks it up, downloads each repository into the sealed sandbox, runs the scanners, and reports back over a signed channel.
  • The AI layer runs outside the sandbox, because that is the only side with a network. The reader and the council are wired in there, and can be switched off entirely with one setting.

The models, as configured today. The reader is an unbranded preview called ox-alpha on OpenRouter, with a chain of stable free models behind it in case it disappears. The council is drawn from separate companies: the same reader model, Google's Gemini, an open GPT model on Groq, and a Qwen model. Free model names change often, so these are overridable and the report always states what actually ran.

Why it is free, and what that costs

Everything runs on free tiers: Cloudflare, GitHub Actions, and free model APIs. That is a deliberate constraint, and it is why the DeepScan is rationed. It also means the honest limits below are real:

  • The best reader model is an anonymous preview that could vanish or start charging at any time. The tool falls back to weaker models rather than breaking when that happens.
  • The daily DeepScan number on the front page counts down as repositories are deep-read, charged at a modeled per-repository cost rather than metered from the providers, so it is honest about the day but approximate about the minute.
  • Dependency vulnerabilities are not checked yet, so a report saying nothing was found is not a promise your code is secure.

Privacy and use

What is stored, what is sent to which provider, and how to have a report deleted are all set out on the privacy page. What is and is not allowed, including scanning accounts other than your own, is on the acceptable use page. The whole thing is open source.
